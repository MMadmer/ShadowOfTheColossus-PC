# Модель памяти ПК (вариант C) — поэтапный план

Запрос пользователя от 27/10/2026, после измерения просадок при входе в новые области (DMA
83–127 мс, отправка 70–106 мс, ожидание чтений GPU 47–59 мс за окно 5 с; VRAM 6,4–7,1 ГБ из 8 ГБ;
поток отрисовки 27–36 мс на кадр при 30 FPS, режим Pro + «Максимум» + DLSS).

## Идея

Сейчас память игры и память GPU разделены: то, что пишет игра, копируется в VRAM (синхронизация
DMA, отправки), а то, что пишет GPU и читает игра, возвращается копированием (чтения GPU с защитой
страниц и ожиданием). В «модели памяти ПК» GPU использует память игры **там, где она находится**
(ОЗУ, импортированная через `VK_EXT_external_memory_host`), и в VRAM зеркалируется только то, что
читается постоянно.

Образец: порт Bloodborne (deadinside28, 0.5–0.6, `docs/NVIDIA_MEMORY_MODEL.ru.md` в
`ref/deadinside28_bloodborne_pc`). Там модель стала режимом по умолчанию на всех видеокартах в 0.6
(19/10), но они переписали всё ядро GPU целиком. Наше использует ядро shadPS4: переносится идея,
а не код. Их уроки, применимые здесь:

- **расхождение** копии в VRAM с памятью игры приводило к «взрывам» вершин и текстурам с мусором;
  каждую запись CPU, проходящую мимо порта, нужно отслеживать (ловушки на запись);
- GPU должен писать в VRAM только в блоки, которых CPU не касался с момента выделения;
- импорт памяти хоста закрепляет страницы в ОЗУ: импортировать частями, по запросу, а не 9 ГБ.

Прототип `tools/host_import_test.c` (08/10) показал на RTX 2060 SUPER: импорт от 256 MiB до 5 GiB
работает, когерентен в обоих направлениях, GPU читает со скоростью 5,5 ГБ/с.

## Этапы (каждый измеряется перед следующим; всё за `SOTC_PC_MEMORY`, по умолчанию выключено)

| № | Этап | Результат | Измерение | Риск |
|---|---|---|---|---|
| 1 | Импортировать память игры в GPU | расширение включено; части по 64 MiB представления `backing` импортируются по запросу как `VkBuffer`; проверка когерентности при инициализации | журнал: импорт выполнен, время, тип памяти; в игре ничего не меняется | низкий |
| 2 | Чтения GPU прямо в память игры | `BeginAsyncReadback` копирует из VRAM в импортированную часть, без промежуточной области и без `memcpy` | мс/с чтений, FPS в демо и в сохранении пользователя | низкий |
| 3 | «Честные» метки завершения работы | метка (EOP), которую ждёт игра, записывается, когда GPU завершает работу, только для измеренных случаев | FPS, отсутствие зависаний | средний (уже пробовали 12/10 как `SOTC_EOP_DEFER`: FPS упал вдвое; нужна избирательность) |
| 4 | Области, читаемые каждый кадр, записываются на месте | отсечение по видимости (битовая маска XPR, ~0x1078c10000) и другие «горячие чтения» записываются GPU прямо в импортированную ОЗУ: без защиты, без обратного чтения | ожидания чтений → ~0; FPS на мосту и в конце демо | средний/высокий |
| 5 | Данные, записываемые CPU, читаются на месте | константы и динамические вершины читаются из импортированной ОЗУ вместо синхронизации через DMA; зеркало в VRAM только для того, что читается постоянно | затраты на DMA (сейчас ~47 мс/с), просадки при смене области | высокий |

**Ограничение, обнаруженное на этапе 1 (27/10):** обратные чтения применяют данные через
`ApplyDownloads`, где находится защита кучи игры (`BpeHeapGuard`, #146, вылет 0x49500 в финале):
устаревшие байты от GPU не должны попадать в блоки, которые игра уже освободила. Копирование GPU
прямо в память игры обходит эту защиту. Поэтому этап 2 пишет напрямую **только за пределами
защищённых куч**; внутри них остаётся текущий путь. То же относится к этапам 4 и 5.

Критерии отсечения: идентичное изображение на захватах демо, ни одного зелёного блока (храм
6-го колосса), финал игры без вылета (POOL_FIX, защиты куч и правило пула не затронуты).

## Состояние

- 27/10: план написан.
- 27/10: **этап 1 готов** (`SOTC_PC_MEMORY=1`, по умолчанию выключено).
  `VK_EXT_external_memory_host` запрашивается только с этим переключателем;
  `renderer_vulkan/sotc_guest_memory.*` импортирует представление `backing`
  (`runtime_memory_backing_view`) частями по 64 MiB по запросу. Представление появляется только
  после того, как игра отображает память, поэтому его ищут при каждой отправке
  (`Rasterizer::OnSubmit`), пока не найдут. На RTX 2060 SUPER:
  `10176 MiB of game memory, 159 chunks ... chunk 0 in 24.2 ms` (тип памяти 3), демо на 60 FPS, без
  ошибок. Список расширений устройства вырос с 32 до 48 мест (запрошено 33).
- 27/10: **этап 2 отменён** (запрос пользователя: самый безопасный вариант, защищающий финал).
  Защита куч в момент применения решает, какие блоки игра только что освободила (кучи мира растут
  частями по 1 MiB, область перестраивается каждые 250 мс–2 с); копирование GPU прямо в память
  выпадает из-под этого контроля. Выигрыш к тому же мал (~3–5% потока отрисовки; ожидание
  остаётся).
- 27/10, измерение (`SOTC_RB_STATS=1`, сохранение пользователя, игровой процесс без движения,
  60 FPS, Pro + DLSS): обратные чтения по инструкциям игры за ~3 мин: `eboot+0x1a6d60` (отсечение
  по видимости) ~50 тысяч в `0x109f83…–0x109f8a…`; `eboot+0x101a98` ~22 тысячи вразброс в
  `0x13…`; `eboot+0x937fd` ~2,6 тысячи в `0x1245620000`. Буфер отсечения **не фиксирован** (14/10
  он был в `0x1078c1…`): он выделяется в **пуле страниц по 64 KiB** (`0x10…`–`0x123C…`, том самом,
  что у `POOL_FIX`), а не в куче (защищённая куча начинается с `0x123c000020`, 150 МБ). Пул
  освобождает и повторно использует страницы: прямая запись безопасна только с честным сигналом
  завершения работы.
- **Новый порядок:** (a) честный EOP только для работы отсечения (риск: замедление, никакие данные
  не меняют места); (b) затем прямая запись только в страницы, которые использует отсечение, с
  проверкой в каждом кадре, что они по-прежнему принадлежат ему. Всё по умолчанию выключено; финал
  игры проверяется пользователем, прежде чем это станет режимом по умолчанию.
