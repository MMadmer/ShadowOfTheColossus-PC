# Путь B: оптимизации GPU из bbport в shadPS4 SotC

Исходный запрос: перенести в наш shadPS4 оптимизации GPU из bbport, такие как конвейер отрисовки
в двух потоках и FSR.

## Что показали тесты (07–08/10/2026)

Нативный порт сначала запускался с видеоядром bbport, в котором есть ~40 оптимизаций,
отключаемых через `BB_TOGGLE_FILE` и перечисленных в `gpu/shim/bbport_toggles.h` в bbport.

| Оптимизация bbport | Влияние на Shadow of the Colossus |
|---|---|
| `PendingFenceWaits` (бит 39) | периодический чёрный экран при загрузке (50–75% запусков) |
| `DrawPipeline`, `DrawPreparation` и подобные (опережающая и отложенная подготовка) | устаревшее или мусорное состояние GPU во время потоковой загрузки при загрузке сохранения: недопустимые шейдерные программы, `Unpack10_11_11`, device lost |
| ослабленные чтения GPU (по умолчанию в bbport) | игра зависает; SotC требует точных обратных чтений (`BB_READBACKS=2`) |

С видеоядром форка вместо видеоядра bbport (при сохранении загрузчика и среды выполнения bbport)
игра стала работать корректно: меню, сохранение и открытый мир, 10 мин без вылета. Эти
оптимизации предполагают, что игра не читает на CPU то, что GPU только что записал. Это верно для
Bloodborne, но не для SotC.

## Текущие измерения (нативный порт, i9-13900K + RTX 2060 SUPER, 1080p)

- По умолчанию: фиксированные 30 FPS, как на PS4; 22–25 при загрузках и в храме.
- Режим `fps60` (vblank 120 Гц): 38 FPS в открытом поле, ~25 в храме.
- Узкое место: поток `GpuCommandProcessor` занят на 72%. Время уходит на драйвер Vulkan и на
  ожидание fence при точных чтениях. Рабочие потоки заданий игры загружены на 36–43%.
- Форк в shadPS4 работал на 17–18 FPS (сводный документ), так что нативный порт уже даёт
  ~1,7x производительности.

## Вывод

Перенос двухпоточного конвейера bbport в форк в неизменном виде сломал бы SotC по причинам,
указанным в таблице. FSR не даёт выигрыша, потому что игра уже рендерит в нативном 1080p.

Нативный порт и форк теперь используют **одно и то же видеоядро** (файлы в
`gpu/shadps4/video_core` взяты из форка). Поэтому любая оптимизация, сделанная здесь, действует
для обоих. Реальный путь — оптимизировать это общее ядро по одной части за раз, с A/B-тестами:
`tools/sotc_hangtest.py` и маршрут с загрузкой сохранения в `tools/sotc_play.py`.
Кандидаты в порядке возрастания риска:

1. Чистые кэши bbport, без отложенной обработки: `RegionCache`, `FetchShaderCache`,
   `ImageDescCache`, `FindImageCache`, `TextureBindingMemo`, `RenderStateMemo`.
   Они снижают затраты потока команд.
2. `ThreadedRecording` (запись команд Vulkan в другом потоке) с сохранением строгого порядка
   относительно точных чтений.
3. Более дешёвые точные обратные чтения: копировать только прочитанные страницы и ждать нужный
   fence вместо ожидания простоя GPU.

Каждый пункт — ручное слияние ядер, разошедшихся на ~17 тысяч строк. Ожидаемый выигрыш — в режиме
60 FPS: режим по умолчанию уже достигает 30 FPS, как на PS4.

## Память игры на месте: прототип (08/10/2026)

В оригинальном bbport (deadinside28, версия 0.3) есть «модель памяти ПК» (`BB_GUEST_IN_PLACE`):
GPU использует память игры там, где она находится, а метки EOP записываются, когда GPU
действительно завершил работу. Так исчезают копирование в VRAM, защита страниц и обратные чтения.
Измерено в Bloodborne: 95 → 115–124 FPS в тяжёлых сценах. Там используется dma-buf, который есть
только в Linux и работает только на AMD.

В Windows для этого служит `VK_EXT_external_memory_host`. Тест `tools/host_import_test.c`
отображает секцию файла подкачки так же, как это делает `src/runtime_memory.c` (представление
«backing» и представление игры поверх placeholder), и импортирует представление «backing».
Результат на RTX 2060 SUPER:

| Размер | Импорт | GPU пишет → CPU видит | CPU пишет → GPU читает | GPU читает импортированную память |
|---|---|---|---|---|
| 256 MiB | да (50 мс) | да | да | 5,4 ГБ/с |
| 2 GiB | да (460 мс) | да | да | 5,7 ГБ/с |
| 5 GiB | да (1,5 с) | да | да | 5,5 ГБ/с |

Тип памяти — host-coherent, без кэширования на CPU, минимальное выравнивание — 4 KiB. Копирование
VRAM→VRAM шло со скоростью 65–184 ГБ/с. Поэтому текстуры и геометрия остаются в VRAM; выигрыш
касается данных, которые GPU записывает, а CPU читает (сейчас для этого нужны точные обратные
чтения), и меток.

**Предлагаемая интеграция по измеримым этапам:**

1. При инициализации импортировать всё представление «backing» как одну `VkDeviceMemory`.
2. Сделать так, чтобы обратные чтения копировали данные из VRAM прямо в память игры, без
   промежуточного буфера и без memcpy. Риск низкий, выигрыш небольшой, но это проверяет
   компонент.
3. Перенести в импортированную память области, ставшие «горячими обратными чтениями» (те, которые
   игра перечитывает каждый кадр). GPU начинает писать в них напрямую, без защиты страниц и без
   обратного чтения.
4. «Честные» метки EOP (записываемые после завершения работы на GPU) для этих областей. Тогда
   достаточно собственной синхронизации игры.
